# Karaoke Party — Development Guidelines

## Project

Karaoke Party — семейная браузерная party-игра с музыкальными и караоке-режимами.

Основные интерфейсы приложения:

- TV Screen — основной игровой экран для телевизора или большого монитора.
- Host — интерфейс ведущего для управления игрой.
- Player — интерфейс игрока на смартфоне.
- Admin — управление песнями, игровыми наборами и контентом.

Backend является источником истины для состояния игры.
Клиенты синхронизируются с backend через REST API и WebSocket.

## Development Principles

1. Пиши простой, понятный и поддерживаемый код.
2. Не создавай лишние абстракции заранее.
3. Не усложняй решение ради архитектурной "красоты".
4. Не добавляй проверки для невозможных или искусственных сценариев.
5. Избегай overengineering.
6. Используй понятные названия переменных, функций и компонентов.
7. Функции и компоненты должны иметь одну понятную ответственность.
8. Не создавай огромные компоненты.
9. Повторяющийся код выноси только тогда, когда повторение реально появилось.
10. Не используй `any` в TypeScript без необходимости.
11. Не добавляй зависимости, если задачу легко решить существующими средствами.
12. Backend является источником истины состояния игры.
13. Клиенты не должны самостоятельно вычислять критическое состояние игры.
14. Все realtime-изменения состояния игры проходят через backend.
15. Код должен быть удобен для дальнейшего добавления новых игровых режимов.
16. После каждого изменения запускай доступные проверки типов, lint и tests.
17. Не исправляй несвязанный с текущей задачей код без необходимости.
18. Перед крупным изменением сначала изучи существующую реализацию.

## UI Guidelines

Используй Ant Design для стандартных UI-компонентов:

- формы;
- таблицы;
- модальные окна;
- Select;
- Input;
- Dropdown;
- Notification;
- Tabs;
- Pagination;
- административные интерфейсы.

Не пытайся строить весь игровой интерфейс только из Ant Design.

Для следующих элементов преимущественно используй собственные компоненты и SCSS Modules:

- TV Screen;
- scoreboard;
- игровые карточки;
- кнопки ответа;
- таймеры;
- игровые состояния;
- анимации и визуальные эффекты.

Не создавай собственный аналог стандартного UI-компонента, если подходящий компонент Ant Design уже решает задачу.

Настраивай внешний вид Ant Design централизованно через `ConfigProvider` и theme tokens.
Избегай глобальных CSS overrides компонентов Ant Design без необходимости.

## Frontend Guidelines

- Используй функциональные React-компоненты.
- Используй TypeScript для компонентов, hooks, store и API.
- Используй Zustand только для действительно общего состояния.
- Локальное состояние компонента оставляй локальным.
- Не помещай всё состояние приложения в один огромный store.
- Не выполняй API-запросы непосредственно внутри UI-компонентов, если логика начинает усложняться.
- Стили компонентов размещай рядом с компонентами в `.module.scss`.
- Общие стили и переменные храни отдельно.
- Учитывай, что Player и Host должны удобно работать на смартфонах.
- TV Screen проектируй прежде всего для экранов 16:9.

## Backend Guidelines

- FastAPI отвечает за REST API и WebSocket.
- SQLAlchemy используется для работы с данными.
- SQLite используется как основная БД на начальном этапе.
- Не создавай repository/service/use-case слои только ради наличия слоёв.
- Выноси бизнес-логику из API handlers, когда она становится самостоятельной логикой.
- Game Engine не должен зависеть от React или конкретного UI.
- Не доверяй клиенту изменение счёта или критического состояния игры.

## Realtime Guidelines

Backend является источником истины.

Через WebSocket синхронизируются:

- подключение и отключение игроков;
- состояние комнаты;
- начало и завершение игры;
- начало и завершение раунда;
- текущий вопрос;
- действия игроков;
- результаты;
- изменение счёта.

После переподключения клиент должен иметь возможность получить актуальное состояние комнаты.

Не добавляй Redis, RabbitMQ или другую realtime-инфраструктуру, пока она действительно не понадобится.

## Working With Existing Code

Перед изменением существующего функционала:

1. Изучи связанные файлы.
2. Определи существующий поток данных.
3. Используй существующие паттерны проекта, если они подходят.
4. Не переписывай рабочий код без причины.
5. Делай минимальный набор изменений, необходимый для задачи.

После реализации:

1. Проверь TypeScript.
2. Запусти lint.
3. Запусти относящиеся к изменению tests.
4. Проверь production build frontend, если изменение затрагивает frontend.
5. Исправь ошибки, вызванные своими изменениями.
